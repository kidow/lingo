# 弊의 15획·14획 차이 검토

검토일: 2026-09-13. 대상: 3급II 弊(u5f0a), 배정표 5316행.

## 결론

앱의 획수를 **15 → 14**로 보정한다. 한국어문회의 후속 상담 답변은 㡀를 7획으로 계산하고, 그 기준을 弊 등에도 적용하여 기존 자전·교재의 집계를 바로잡아야 한다고 설명한다. **弊의 14획은 이 설명에 따른 㡀 7 + 攵 4 + 廾 3의 합**이다. 답변이 문자 그대로 ‘弊 14획’이라고 표기한 것은 아니다.

2026-09-13 다시 내려받은 공식 XLS는 여전히 弊를 15획으로 표기하며, 최초 수집본과 바이트 해시가 같다. 따라서 원자료를 잘못 읽은 문제가 아니다. 후속 설명과 아직 갱신되지 않은 배정표 사이의 차이다. 원문 값 15는 `sourceStrokes`, 보정 근거는 `strokeCountCorrection`으로 보존한다.

## 근거와 해석의 구분

1. [한국어문회: 敝와, 敝가 들어간 한자들의 획순](https://www.hanja.re.kr/klea/counsel/hanjaDetail.do?id=16411), 2025-08-21. 질문에 弊가 포함되어 있고, 답변은 㡀 안의 巾 세로획이 하나임을 설명한다. 이 답변만으로 총획 정정을 명시했다고 해석하지 않는다.
2. [한국어문회: 敝가 攴부 8획으로 여겨지는 까닭](https://www.hanja.re.kr/klea/counsel/hanjaDetail.do?id=16424), 2025-09-13. 답변은 㡀를 7획으로 계산해야 한다고 명시하고 弊·幣·蔽·斃·瞥·鼈·鱉에도 같은 기준을 적용한다. 기존 8획 집계와 교재의 敝 12획 표기를 바로잡아야 한다는 설명이다. 예서체에서 8획 집계가 비롯되었을 가능성은 답변자의 추정이며, 모든 자전의 집계 원인으로 확정하지 않는다.
3. [한국어문회 급수 배정표](https://www.hanja.re.kr/kccpt/exam/levelConfirm.do). XLS의 5316행은 `弊 / 廾 / 부수 외 12획 / 총 15획`이다. 재수집본 971,264바이트, SHA-256 `97b8db715ebe1dd6e00e8e58d338a9ba70e7420bf5ec84da38f987d60eb64b17`. 실제 XLS 파서는 xlrd 2.0.2를 사용했다.
4. 앞선 교과서·사전 검토에서도 弊는 14획이었다. 사전 SVG를 재확인한 결과 제목과 14개의 획 타이밍 및 파일 해시가 기존 기록과 같았다. 이번에는 공식 설명과 획수의 충돌을 해소했으며, 전체 경로를 새로 육안 검수한 것은 아니다.

출처의 URL, 수집 크기·해시, 원본 행과 이전 검토 파일의 해시는 [sources.json](sources.json)에 기록했다. 외부 HTML·이미지·영상 원본은 이 보고서에 복제하지 않았다.

## 적용 범위

- 弊 한 글자의 획수 및 원문 보존 필드만 바꾼다. 식별자·급수·훈음과 두 학습 기록 키는 유지한다.
- [보정 목록](../../content/hanja/stroke-count-corrections.json)과 [원자료 검증기](../../scripts/hanja-source.py)가 같은 보정을 사용한다. 원본 파일 해시, 행 번호, 원문 자형 또는 획수가 바뀌면 재검토를 요구한다.
- 획수 보정은 애니메이션 승인과 별개다. 현재 弊는 승인된 경로가 없어 여전히 재생되지 않는다. 기존 14획 자료를 억지로 15획으로 나누지 않는다.
- 공식 답변에 함께 등장하는 다른 글자는 이번에 일괄 변경하지 않았다. 같은 XLS에서 敝12·幣15·蔽16·斃18·瞥17도 확인되어 별도 검토 후보로 남긴다. 각 글자의 다른 구성요소·등록 자형과 승인 경로를 함께 확인해야 한다.
- 과거 15획 기준으로 작성한 검토 파일은 당시 판단의 기록으로 보존한다. 새 경로 검토는 이번 정정 기록을 참조해야 한다.

## 검증

```sh
rtk proxy python3 -B scripts/hanja-source.test.py
rtk proxy node --test 'lib/hanja*.test.ts'
rtk proxy pnpm exec next build
```

Python 단위 검사는 네트워크·XLS 파서를 대체해 원본 행의 정규화와 변경 감지만 검증한다. 실제 XLS 재수집·파싱은 별도로 완료했다. 최종 실행 결과는 [verification.json](verification.json)에 기록한다.
