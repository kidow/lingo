# 진도 동기화

진도가 localStorage에만 있어 **기기마다 다르게 나오는** 문제를 푼다.
spec.md §4가 "DB는 로그인과 진도 동기화가 필요해질 때 도입한다"고 적어 둔 그
시점이다. §11의 `DB 도입`·`로그인` 두 행이 여기로 온다.

## 안 바꾸는 것 셋

**`output: 'export'`는 그대로다.** Supabase JS는 브라우저에서 돈다. API
라우트도 서버도 필요 없고 RLS가 막는다. 주소와 키는 `NEXT_PUBLIC_AUDIO_BASE`로
R2를 가리키는 지금 방식과 같게 환경변수로 넣는다 (`.env.example`).

**localStorage는 남는다.** 서버는 사본이지 원본이 아니다. 비행기에서도 돌아야
하고 네트워크가 죽었다고 학습이 멈추면 안 된다. `loadProgress`·`saveProgress`의
계약은 그대로다 (lib/progress.ts).

**로그인 벽은 없다.** 열면 바로 공부가 시작된다. 로그인하지 않은 사람은 지금과
똑같이 돌고 동기화만 없다. 지금은 허용 목록이 한 명이라
(supabase/migrations/…_reviews.sql) 사실상 나만 동기화된다.

## 왜 스냅샷이 아니라 로그인가

지금 `Progress`는 **현재 상태**다 — `rung`·`streak`·`fsrs`. 그대로 올리면
통짜 LWW가 되어, 폰에서 20장 노트북에서 30장을 봤을 때 20장이 사라진다.
**지금보다 나쁘다** — 지금은 최소한 각 기기가 자기 것은 지킨다.

대신 일어난 일을 쌓는다. 셋이 따라온다.

**병합이 합집합이다.** 양쪽 로그를 합치고 갈라진 카드만 시간순으로
`scheduler.next()` 재생한다. 카드 하나에 복습이 스무 번이면 재생도 스무 번이고
전체를 다시 돌리지 않는다. 잃는 복습이 없다.

**추적이 여기서만 나온다.** 스냅샷은 지금 상태만 안다. 지난주에 몇 장 했는지,
정답률이 오르는지, 어떤 낱말을 반복해서 틀리는지는 전부 로그가 있어야 답이
나온다. `/debug`의 커버리지 표가 콘텐츠를 세듯 학습을 셀 수 있게 된다.

**되돌릴 수 없다.** 로그에서 스냅샷은 뽑히지만 스냅샷에서 로그는 못 뽑는다.
나중에 바꾸면 그때까지의 이력이 영영 없다.

## 걸리는 자리 — 세션 중간 병합

`loadProgress`는 동기고 서버는 비동기다. 당겨온 것을 아무 때나 `setProgress`
하면 **보고 있던 카드 뭉치가 갈린다** — 피드는 진도를 보고 한 칸 앞까지만
카드를 만들기 때문에(components/feed.tsx의 `extendOne`) 중간에 진도가 바뀌면
이미 화면에 있는 카드와 어긋난다.

그래서 **병합은 마운트와 트랙 전환 때만** 한다. 그 뒤 도착하는 원격 변경은
다음 전환까지 큐에 재운다. 피드는 이미 `track`·`entries`가 바뀌면 통째로 다시
만들므로(`useEffect`에서 `initialState(loadProgress(track))`) 그 자리에 붙는다.

## 덤 — 5MB 한도

여덟 트랙을 다 공부하면 localStorage가 6MB인데 한도가 대개 5MB다
(lib/progress.ts의 `saveProgress`가 지금은 토스트로 알려 주는 게 전부다).
사본이 서버에 있으면 로컬은 지금 트랙만 들고 있어도 되므로 이 문제가 같이
풀린다. **먼저 하지 않는다** — 동기화가 확실히 돈 뒤에 버려야 한다.

## 손으로 해야 하는 것

마이그레이션이 못 하는 설정이 둘이다.

1. **공개 가입 끄기** — Authentication → Sign In / Providers → 이메일만 켜고
   "Allow new users to sign up"을 끈다. 트리거가 뒤에서 한 번 더 받지만
   (`reject_unlisted_signup`) 그건 설정이 풀렸을 때를 위한 그물이다.
2. **첫 사용자 만들기** — 가입을 껐으므로 대시보드에서 직접 넣는다.
   클라이언트는 `signInWithOtp({ shouldCreateUser: false })`로 부르므로
   없는 계정은 로그인 자체가 시작되지 않는다.
